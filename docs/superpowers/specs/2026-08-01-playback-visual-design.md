# 播放視覺設計：分段取景 + 交通工具圖示

> **狀態：設計已定調，尚未實作。** 2026-08-01 與使用者定案，出發前不做，回國後排。
> 使用者原話：「我要的飛機飛行也是第一種，就是看得出來是哪種交通工具在移動，另外可能要針對當下的場景大小做微幅調整，像第一天是從台灣飛到日本，然後在福岡轉機到鹿兒島，像這種的飛行就不能用相同比例尺，我想要的效果就是可能可以按照旅行的距離區分我們全景移動的大小」

---

## 核心設計：以「當前交通段」為取景單位

**取代**先前定案的「起播 fitBounds 一整天」。理由：同一天內各段距離量級差異可達三個數量級（台北→福岡約 1,000km、福岡→鹿兒島約 200km、博多站→中洲約 1km），用同一比例尺會讓短段完全看不出在動。

播放推進到某一段交通時，鏡頭以**該段的起訖兩點**取景：

| 段落 | 取景範圍 | 概略 zoom |
|---|---|---|
| 台北 → 福岡（航班） | 兩個機場 + 海峽 | 6-7 |
| 福岡 → 鹿兒島（航班／新幹線） | 兩點 | 8-9 |
| 博多站 → 中洲（步行） | 兩點 + 周邊街廓 | 15-16 |

停留期間（非移動中）的取景策略**待定**，兩個候選：(a) 維持前一段的框不動；(b) 收近到該停留點。建議 (a)——減少鏡頭動作，且停留點的細節在時間軸上已有呈現。

## 為什麼這比原方案更安全（不是取捨）

2026-08-01 的灰塊事故根因是「3 秒內鏡頭跳 3 次、前後視窗零重疊」，圖磚永遠來不及載入。分段取景的換鏡頭頻率是**每段一次**（一天約 3-8 次），中間隔著數秒的段內播放時間 → 圖磚有充裕時間載入。**使用者要的效果與系統穩定性方向一致。**

仍需保留的護欄：
- 段內橘點移動一律不動鏡頭（沿用已實作的邊緣閘門作為安全網）
- 換段時的比例尺跳躍**待決**：瞬間切換 vs 動畫過渡。註記——若用 `panTo`/動畫在 zoom 6 與 zoom 16 之間過渡，會經過大量中間層級的圖磚，反而是灰塊的溫床。**建議瞬間切換或淡入淡出**，不做連續縮放動畫。
- `PLAYBACK_MAX_ZOOM = 15` 的夾制需重新檢視：步行段可能需要放寬到 16-17

## 交通工具圖示

播放頭目前是橘點，改為依**當前段落的 `legs.mode`** 切換圖示，並朝行進方向旋轉：

| mode | 圖示 |
|---|---|
| `walking` | 🚶 |
| `transit` | 🚃 |
| `driving` | 🚗 |
| `flight` | ✈️ |
| `custom` | 保留橘點或 📍 |

停留期間（不在任何 leg 上）維持橘點。

實作提示：圖示選碼位時避開需要 U+FE0F 變體選擇子者（跨平台會變黑白字元）——與 Plan 7 分類圖示同一條約束。

## 路線繪製（材料已存在，從未使用）

`legs.polyline` 欄位**已經存了 Google Routes API 回傳的路線幾何，但全 app 無任何渲染路徑**（多份審查獨立指出：`TripView.tsx:54` 只有型別宣告）。Plan 5 Task 9「地圖 polyline」即為此，一直未輪到。

- **有 polyline 的段**（transit/walking/driving）：解碼後依播放進度**漸進繪製**——只畫已經走過的部分，前端接圖示。這就是「印第安納瓊斯紅線」效果
- **航班段**：Google 不提供航線，改用兩點之間的**弧線 + 虛線**，是刻意的視覺語言，一看就知道是飛機
- ToS：polyline 屬 Google 衍生內容，受 30 天快取限制；現有 sync 機制的 TTL 即為 30 天，渲染不逾越。**但不得進定稿快照／匯出**（`snapshot.ts:10` 已明文排除，維持該決定）

## 明確不做（本階段）

**Google 地球式飛行運鏡**（鏡頭傾斜、俯衝、繞地標旋轉）。理由：
1. 它本質是「讓鏡頭大幅快速移動」，正是灰塊事故的成因
2. 要做好需要控制移動速度、預載沿途圖磚、換掉現在的 `mapId="DEMO_MAP_ID"` 示範樣式
3. 屬獨立的專案級工作，不是順手加的效果

使用者已理解並同意：「我覺得定格全景不錯」→ 後續細化為本文的分段取景。紀錄片感的主體是**線在長**，不是鏡頭在飛。
