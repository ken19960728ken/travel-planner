## 起因

`plan5/task8-share`（分享預覽：免註冊唯讀連結）的 db-expert 審查發現：**移除成員不會使分享連結失效**，但 UI 顯示「該行程所有邀請連結已一併撤銷」。使用者由此追問分享連結的權限判斷機制，延伸出兩個提案。

## 現況機制（事實）

分享連結的權限判斷是**一句 SQL**：

```sql
-- supabase/migrations/20260806000000_share_rpc.sql（分支 plan5/task8-share，尚未合併）
create function public.get_shared_trip(p_token uuid) returns jsonb
language sql security definer stable set search_path = public as $$
  select jsonb_build_object(...)
  from trips t where t.share_token = p_token
$$;
```

沒有 `auth.uid()`、沒有查 `trip_members`、沒有角色判斷。`security definer` 讓它以擁有者（postgres）身分執行，而所有表 `relforcerowsecurity = false`，故**RLS 在這條路徑上完全不被詢問**。

**「知道那串亂數」本身就是權限**——持有者憑證（bearer/capability token）模型，等同 Google 文件的「知道連結的人都能看」。

對照：登入路徑走 RLS + `is_trip_member` / `is_trip_editor` / `is_trip_owner`（`20260730000000_init.sql:57-80`），三者都從 `auth.uid()` 查 `trip_members` 決定角色。

### 這個模型擋得住的
- token 為 `gen_random_uuid()`，122-bit 熵，列舉不可行（`trips_share_token_key` 唯一索引）
- 錯誤 token 回 null，且「從未存在」與「已重生成」不可區分（原地 UPDATE 不留歷史），無 oracle
- anon 對九張表的讀寫改刪端到端全 401（db-expert 逐表實測）
- 分享頁 `robots: {index:false}` + `referrer: 'no-referrer'`，token 不從搜尋結果或 Referer 外洩

### 這個模型放掉的（設計本質，非 bug）
- **不知道是誰在看** → 無法記錄、無法只撤銷某一人
- **唯一撤銷方式是重生成 token** → 所有人一起失效
- **轉發無法偵測也無法阻止**

→ 「移除成員」走的是成員身分那套機制，而分享連結**根本不查成員身分**。兩者正交，所以踢人對分享連結**在設計上就不可能有效果**。目前的 UI 文案給了錯誤的安全感。

## 提案 A（使用者）：連結綁定身分，訪客進來就註冊一個身分，註銷該身分即作廢連結

**評估：綁定「訪客」行不通——你無法驗證一個從未驗證過的人。** 三種實作各自的失敗模式：

| 實作方式 | 失敗模式 |
|---|---|
| 要求登入才能看 | **這就是現有的邀請功能**（`trip_invites` + `accept_trip_invite`，已上線）。但「免註冊」是分享連結存在的唯一理由，加上登入等於此功能消失 |
| 發匿名 cookie 當身分 | 身分在訪客手上：清除瀏覽資料、無痕視窗、換裝置都是全新身分。更根本的是他手上有**原始網址**，直接轉發網址即可繞過。擋不住任何想繞過的人 |
| 首次開啟即綁定瀏覽器（TOFU） | 真實世界壞得最慘：自己手機測試後電腦打不開；LINE/Slack 收到網址會**自動抓取做預覽卡片**，那一抓就把綁定用掉，真人反而被鎖在外面 |

---

## 反提案：具名分享連結（綁發送端，不綁接收端）

問題本質不是「不知道訪客是誰」，而是**一條連結對應所有人**，所以撤銷只能全有或全無。把身分放到**發送端**即可解決。

**設計草案（未定案）**：不再只有 `trips.share_token` 單欄，改為 `trip_share_links` 表——`id / trip_id / token / label（「給小明」「貼家族群組」）/ created_by / created_at / expires_at / revoked_at`。owner 看得到清單，可單獨作廢其中一條。

- 轉發**仍擋不住**（持有者憑證的本質），但災情從「全有全無」變成「知道是哪一條外流，砍掉它就好」
- 同類模式：GitHub deploy keys、各家服務的 API token
- 可選加值：`expires_at`（如 7 天自動失效）——純資料庫欄位，複雜度幾乎為零，比綁身分實在

### 三層並存（建議，非互相取代）

| | 要登入 | 撤銷粒度 | 適合 |
|---|---|---|---|
| 邀請旅伴（已上線） | 要 | 逐人，乾淨 | 一起規劃的人 |
| 具名分享連結（提案） | 不用 | 逐條連結 | 傳給特定對象看 |
| 單一公開連結（現況） | 不用 | 全有全無 | 貼群組、隨便誰看 |

**時程判斷**：新表 + UI + RLS + 一輪完整審查，出發前做不完。定位為回國後的 Plan 8 候選。

## 提案 B（使用者）：立系統鐵律——沒登入不能共同編輯

使用者原話：「身份可以決定只能看不能編輯，沒有登入的訪客不能共同編輯同一份旅遊項目……如果沒有登入的訪客只能自己編輯自己的行程，沒有共同編輯的選項，看要不要把這個加入系統的鐵律中」

### 評估：該立，且第一半已經是現實

anon 對 `trips` / `stops` / `legs` / `trip_members` / `trip_invites` / `trip_candidates` / `trip_snapshots` / `route_cache` / `profiles` 九張表的 SELECT/INSERT/UPDATE/DELETE **端到端全部 401**（db-expert 實測，非只讀 SQL）。強制點在**資料庫授權層**，不是 UI——前端限制被整個拆掉也一樣擋得住。

### 但規則會漏的地方：SECURITY DEFINER 函式繞過一切

授權表擋得住直接讀寫，擋不住 definer 函式——`get_shared_trip` 正是如此（anon 對表零權限，卻拿得到整份行程）。**規則必須補第二句**：

> 任何授予未登入身分的函式，必須是唯讀的。

否則哪天有人為了方便寫一顆「訪客可留言」的匿名函式，前面九張表的零權限全部白費。

### Google 試算表類比的修正

Google Docs/Sheets **其實允許匿名編輯**（「匿名的水豚」那些）。但該功能出名難管：不知道誰改的、無法只踢一人、關掉就是全部一起關。

→ 它不是支持使用者論點的例子，而是**證明使用者判斷優於 Google 預設**的例子。共編天生需要三件事：知道誰改的、衝突時誰贏、要趕人時趕誰——三件都需要身分。本專案已有樂觀鎖（`.eq('updated_at', lockToken)`）與 `updated_by`，沒有身分這兩樣都是空的。

### 措辭建議（避免誤傷未來功能）

原句「未登入訪客只能編輯自己的行程」描述的不是現況——目前**根本沒有訪客模式**，不登入連建行程都不行。建議改為：

> **共同編輯一律要求成員身分；匿名使用者若未來要能編輯，只能編輯不屬於任何帳號的獨立副本。**

這樣既擋住擔心的事，又不會把「訪客先試玩、覺得好用再註冊」這種未來可能想做的功能一起禁掉——那不是共編，不該被此規則誤傷。

### 重要：鐵律**不解決**撤銷問題

兩者正交。鐵律管「能不能寫」，分享連結的麻煩是「**讀**的權限收不回來」。就算永遠唯讀，被移除的成員仍能持續看到行程與備註。鐵律該立（成本幾乎為零、讓系統邊界清楚），但具名連結那件事仍須另外處理。

### 讓它成為真鐵律：兩條可機檢斷言

寫在文件裡的規則會被忘記，能被機器檢查的才叫鐵律。建議與現有測試放一起（約 20 行）：

1. 掃全部資料表，斷言 anon 的 INSERT/UPDATE/DELETE 權限**恆為零**（有人手滑加 grant 就紅燈）
2. 掃所有授予 anon 的函式，斷言全部為唯讀（`provolatile in ('s','i')` 且函式體無寫入語句）
