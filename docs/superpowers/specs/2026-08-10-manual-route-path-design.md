# 手繪交通路徑 — 設計文件

- 日期：2026-08-10
- 狀態：設計已與需求方逐段確認，待排實作計畫
- 相關：`docs/guides/gcp-setup.md`（Google API 限制）、spec §4（資料模型）、spec §8（殘留風險）

## 1. 問題

Google Routes API **不支援日本的大眾運輸**。對日本境內的 transit 查詢，Google 不會回「查無資料」，而是回**一條純步行的路線**。系統偵測到「只有步行、沒有任何搭乘段」後標記 `no_transit_data`，但**同時把那條步行路線的幾何存進 `legs.polyline`**（`src/app/api/trips/[tripId]/legs/sync/route.ts:311-318`，方案 I-2(a)：保留真實步行時長供衝突偵測使用）。

後果：地圖與播放動畫畫出一條沿著馬路蜿蜒、看起來很像真實路線的線——**但那是走路的路徑，不是電車的**。使用者無從得知。

而使用者一旦手動修正該段時間（改成自訂），`LegEditor` 的寫入會把 `polyline` 清成 `null`（`LegEditor.tsx:162`），地圖退回兩點直線虛線。等於「越修正越沒有路線可看」。

## 2. 目標與非目標

**目標**：讓使用者能在地圖上自己點出交通路徑的轉折點，畫出接近實際鐵路／交通走向的線，並在地圖、播放、分享、匯出四處一致呈現。

| 項目 | 本設計 | 理由 |
|---|---|---|
| 手繪路徑（點、拖、插點、刪點） | ✅ | 本文主體 |
| 純視覺——不影響時長與距離 | ✅ | 需求方明確選擇。列車速度差異大，由路徑長度推算時間只會失準 |
| 所有交通段皆可畫 | ✅ | 含 Google 算得出來的段落（例：步行段想畫成實際走的巷弄） |
| 手機可畫 | ✅ | 需求方明確要求（旅途中補畫） |
| 未手繪的 `no_transit_data` 段誠實標示 | ✅ | 見 §7。與本功能同批處理，成本近乎零 |
| 吸附到道路／鐵路 | ❌ | Google 無日本鐵路幾何；道路吸附（DirectionsRenderer draggable）對列車反而更錯，且每次拖曳都是一次計費呼叫 |
| 以 Google 現有路線為底稿再修改 | ❌ | 主要情境是日本電車，底稿是步行路線，以它為起點要刪一堆點，比空白開始慢 |
| 由路徑長度推算距離／時間 | ❌ | 見上「純視覺」 |
| 參與人指派 | ❌ | 獨立功能，見 §10 |

## 3. 資料模型

### 新增欄位，不重用 `legs.polyline`

兩者性質不同，共用會讓既有規則全部失效：

| | `polyline`（Google） | `custom_path`（使用者） |
|---|---|---|
| 資料所有權 | Google | 使用者 |
| 保存期限 | 30 天（ToS，spec §4 資料分層） | 永久 |
| 定稿快照／JSON 匯出 | 明文排除 | **收錄** |
| 自動計算重算時 | 被覆寫 | 不受影響 |

`snapshot.ts:10-11` 目前是靠「輸入型別根本不宣告 polyline 這個鍵」來保證結構上不可能外洩 Google 衍生資料。共用同一欄會直接破壞這個保證。

```sql
alter table public.legs add column custom_path jsonb;
alter table public.legs add constraint legs_custom_path_shape check (
  custom_path is null
  or (jsonb_typeof(custom_path) = 'array' and jsonb_array_length(custom_path) <= 100)
);
```

- **格式**：`[[lat, lng], ...]`，緯度 -90~90、經度 -180~180
- **上限 100 點**：橫跨九州的鐵路線用不到 40 點；100 給足餘裕又讓分享頁 payload 有上界（100 點約 2KB，與 `polyline` 的 4000 字元上限同量級）
- **不用編碼字串**：現有工具只有 `decodePolyline` 沒有編碼器，用 JSON 免寫編碼器與其測試，且 DB 內容可讀、可用 check constraint 驗形狀
- **深層驗證分層**：DB 檢查「是陣列、長度 ≤ 100」（check constraint 無法逐元素迭代）；應用層驗證每個元素是二元數字陣列且座標在範圍內；渲染層防禦性過濾不合法元素（見 §8）

### 只存中間轉折點，頭尾自動接停留點

`custom_path` **不含**起訖點。渲染時：

```
實際畫出的路徑 = [起點停留點座標] + custom_path + [終點停留點座標]
```

好處：使用者之後拖動停留點時，路徑**自動重新接上**，不會出現線與停留點對不齊。

代價（已告知需求方並接受）：**無法把路徑起點畫在離停留點有距離的位置**（例如想從車站另一個出口起算）。第一個轉折點可以放在停留點附近逼近該效果。

### 權限

`legs` **沒有欄位級 GRANT**（已查證），既有 policy `editor 以上可改交通段`（`init.sql:204`）自動涵蓋新欄位，migration 不需額外授權語句。

### 與 auto/manual 狀態正交

畫路徑**不改變** `source`。一個 `source='auto'`（時間由 Google 算）的段落可以有使用者畫的 `custom_path`。sync 只寫 `polyline`／`duration_minutes` 等欄位，**永不觸碰 `custom_path`**，因此重算不會毀掉手繪成果。

## 4. 操作設計

### 入口

「畫路徑」按鈕放在**交通段編輯器內**（`LegEditor.tsx`），不在側欄每一列掛鈕——避免每段都多一顆鈕造成介面擁擠。

### 編輯模式

按下後地圖進入專屬編輯模式，狀態必須明顯可辨：

- 地圖上方浮出工具列：`儲存` `取消` `清除全部` `刪除選取的點`，以及目前點數 `n/100`
- 該段交通的**起訖兩個停留點高亮**
- **其他地圖互動全部停用**：停留點圖釘點擊、右鍵新增自訂停留點、備選圖釘點擊

以「模式」隔離手勢，而非以啟發式猜測使用者意圖——這是手機能用的關鍵。

### 互動對照

| 動作 | 電腦 | 手機 | 實作 |
|---|---|---|---|
| 在末端加點 | 點擊地圖空白處 | 輕點地圖空白處 | `Map` 的 click 事件 |
| 移動頂點 | 拖曳頂點 | 拖曳頂點 | **Google 原生**（`Polyline` 的 `editable: true`）|
| 中間插點 | 拖曳線段中央控制點 | 同左 | **Google 原生**（官方：控制點顯示於「vertices and on each segment」）|
| 刪除頂點 | 輕點頂點選取 → 按工具列「刪除選取的點」 | 同左 | 自訂：`path.removeAt(vertex)`。選取中的頂點以放大 1.5 倍 + 紅色外框標示；未選取時「刪除選取的點」呈停用狀態 |
| 全部重來 | 「清除全部」 | 同左 | 自訂 |
| 放棄 | 「取消」 | 同左 | 還原成進入編輯模式前的狀態 |

**刪點刻意採「選取 → 按鈕」而非右鍵**：右鍵在手機不存在，用同一套操作可避免兩套邏輯與兩套測試。

**地圖平移在編輯模式仍可用**（拖曳 ≠ 輕點，可區分），使用者才能移動到遠處繼續畫。

### 邊界情況

| 情況 | 行為 |
|---|---|
| 播放中按下「畫路徑」 | 先停止播放。兩者搶同一個地圖，不可並存 |
| Realtime 斷線 | 畫路徑是寫入動作，比照其他寫入入口被 `writesBlocked` 擋下 |
| 旅伴同時改同一段 | 沿用 `LegEditor` 既有樂觀鎖（`lockToken`），存檔前發現版本已變則提示重新載入，不覆蓋對方 |

## 5. 渲染整合

四處目前都讀 `leg.polyline`，改為透過**單一優先序函式**取得路徑，避免四份實作各自漂移：

```
路徑優先序：custom_path（使用者）→ polyline（Google）→ 兩點大圓弧（無資料）
```

| 位置 | 檔案 | 變更 |
|---|---|---|
| 選中日靜態路線 | `RoutePolylines.tsx` | 改用優先序函式 |
| 播放漸進紅線 | `TripView.tsx` 的 `completedPaths` / `currentTravelPath` | 同上 |
| 播放頭圖示位置 | `TripView.tsx` 的 `travelPath` | 同上 |
| 分段取景 | `TripView.tsx` 的 `segmentPath` | 同上 |

### 側欄標示與還原

畫過路徑的交通段在側欄顯示 `✏️ 自訂路徑` 標記。編輯器提供「還原成自動路線」——將 `custom_path` 設為 null，Google 的線立即回歸。

### 快照、匯出、分享

- **定稿快照與 JSON 匯出**：**收錄** `custom_path`（使用者資料，不受 30 天 TTL 限制）。需修改 `snapshot.ts` 的輸入型別以顯式納入此鍵
- **分享頁**：`get_shared_trip` 白名單加入 `custom_path`，旅伴看到與擁有者一致的路線

## 6. 元件切分

| 檔案 | 職責 |
|---|---|
| `src/lib/domain/routePath.ts`（新） | 純函式：優先序解析、`custom_path` 格式驗證與清洗、組合頭尾停留點。無 DOM、無 google 全域，可完整單元測試 |
| `src/app/trips/[tripId]/RouteEditor.tsx`（新） | 編輯模式的地圖層：`editable` Polyline 生命週期、頂點事件、工具列。命令式 overlay，比照既有 `RoutePolylines`／`PlaybackTrail` 的 effect 管理慣例 |

| `TripView.tsx` | 編輯模式狀態接線、其他互動停用、四處渲染改用優先序函式 |
| `RoutePolylines.tsx` | 改用優先序函式；`no_transit_data` 視覺區隔（§7）|

`TripView.tsx` 已達 1300 行，本設計刻意把所有新邏輯放進兩個新檔，只在 TripView 留接線。

## 7. 未手繪段落的誠實標示

與本功能同批處理（需求方選擇「一起做」）。

**問題**：使用者沒畫的 `no_transit_data` 段落，地圖仍畫出那條看起來像交通路線的步行路徑。

**處理**：

- 地圖上該段落改為**灰色（`#6b7280`）虛線、透明度 0.5**，與正常的模式配色實線明確區隔。灰色是既有 `custom` 模式的路線色，語義相通（「不確定實際怎麼走」），不新增保留色、不需重跑 ΔE 掃描
- 側欄／交通段編輯器標明「此路線為步行路徑，僅供參考」
- 使用者一旦手繪，該段落改用 `custom_path` 正常樣式呈現，提示消失

**不改動**的部分：步行時長仍照常保留與顯示（衝突偵測需要真實時長，這是 I-2(a) 的既有決策）。

## 8. 錯誤處理

| 情況 | 行為 |
|---|---|
| 存檔失敗（網路／權限） | 提示失敗，**編輯模式不關閉**，使用者畫的內容保留可重試 |
| 樂觀鎖衝突 | 提示重新載入，不覆蓋對方 |
| 達到 100 點上限 | 到達當下停止加點並提示，不是存檔才報錯 |
| 只有 1 個中間點 | 允許。頭尾自動接上即成折線 |
| 0 個中間點時存檔 | 等同「還原成自動路線」，寫入 null |
| DB 內容格式損壞 | 渲染層過濾不合法元素；全部不合法則視為無 `custom_path`，退回 Google 路線。**絕不讓畸形資料造成整頁崩潰** |

最後一條有前例：Realtime 的 presence payload 曾因信任遠端資料形狀而導致整頁崩潰（spec §8 C-1）。本功能從一開始就在渲染層驗證。

## 9. 測試

| 層級 | 內容 |
|---|---|
| 單元（`routePath.test.ts`） | 優先序三分支；格式驗證（非陣列、元素非二元、座標越界、超長）；頭尾組合；空陣列等同無路徑；畸形元素過濾 |
| 整合（Supabase） | `custom_path` 的 check constraint（長度 101 被拒）；editor 可寫、viewer 不可寫；`get_shared_trip` 白名單回傳此欄 |
| E2E | 畫一條路徑 → 重新載入仍在 → 分享頁可見 → 「還原成自動路線」後 Google 線回歸 |
| 手動（自動化無法覆蓋） | 手機實機以手指畫、拖點、刪點；確認與地圖平移不衝突；編輯模式下其他互動確實停用 |

## 10. 後續項目（不在本設計範圍）

**參與人指派**（需求方 2026-08-10 提出）：行程中的每個停留點可標記「誰會參加」，用於共同行程與分頭行動並存的情境——知道誰去了哪裡、花費該算在誰頭上、播放時可只看某個人的路線。

牽涉問題（任一個都可能改變資料模型，故需獨立設計）：

- 「參與人」是已加入的 `trip_members`，還是可含無帳號的同行者名字？
- 指派的粒度：停留點？交通段？兩者？
- 播放：分頭行動時播誰的路線
- 花費：分頭段落的花費是否只計入參與者（spec §4 第 7 點的「每人預估」原意只是總額均分，未模型化參與人）
- 匯出：Excel 是否分人

**排序理由**：參與人會碰到播放、花費、匯出三處，而手繪路徑正好也要動播放。先完成手繪路徑，參與人開工時基礎穩定，不必在兩個未完成的功能上疊加。

## 11. 部署順序

新增欄位屬「**新程式碼要讀新欄位**」類型 → **migration 先推雲端，程式碼後部署**（README 部署段的順序表；本專案 2026-08-03 因搞反此順序造成線上故障）。

migration 編號需大於目前雲端最後一支 `20260805000000`，本設計採 `20260810000000_legs_custom_path.sql`。

分享頁 RPC（`get_shared_trip`）的白名單更新**寫在同一支 migration 檔內**（不另開一支），比照 `20260804000000` 的做法以 `create or replace` 保留既有 ACL，並加 `drop ... if exists` 前綴確保可重跑——本專案存在繞過 CLI 手動貼 SQL 的實務。
